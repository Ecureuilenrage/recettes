## Story

En tant que **développeur de la couche 4 (générateur LLM, `app/generator/`)**,
je veux **une fonction PURE et déterministe `to_markdown(recipe) -> str` (module `app/generator/markdown.py`) qui produit un rendu Markdown LISIBLE par un humain à partir d'un `StructuredRecipe` (contrat D1, consommé en LECTURE SEULE) : un titre `# {title}`, une ligne de portions (`servings`), une section `## Ingrédients` (liste à puces « quantité + unité + nom »), une section `## Préparation` (étapes numérotées avec leur texte), et la restitution VISIBLE des températures (avec leur étiquette `[SÉCURITÉ]`/`[TECHNIQUE]`/`[PRÉFÉRENCE]`), des durées et du cookware quand pertinent**,
afin de **réaliser l'étape « Couche 4 (émission) » du flux (archi §7 : `to_markdown(recipe) → rendu lisible`) qui alimente le champ `GenerationResponse.markdown` (archi §9.1), et de fournir la VITRINE de l'explicabilité (archi §9.2 / barrière 1 §6.1) : le rendu lisible montre clairement les températures de sécurité des protéines et leurs étiquettes, là où `to_cooklang` (D3) produit le pendant « machine » téléchargeable**.

## Acceptance Criteria

1. **AC1 — `to_markdown` produit un Markdown LISIBLE (titre + portions + ingrédients + préparation)** : `to_markdown(recipe) -> str` produit un document Markdown complet et lisible depuis un `StructuredRecipe` : (a) un **titre** `# {recipe.title}` ; (b) une **ligne de portions** mentionnant `recipe.servings` (ex. « **Portions : 4** » — portions de BASE, archi §7) ; (c) une section **`## Ingrédients`** sous forme de **liste à puces** où chaque ingrédient est rendu « quantité + unité + nom » (ex. « - 2 c.à.s d'huile d'olive » ; quantité/unité depuis `Quantity.amount`/`Quantity.unit`, nom depuis `Quantity.name`) ; (d) une section **`## Préparation`** où chaque `Step` est rendue en **liste numérotée** (« 1. … », « 2. … ») avec son `Step.text`. Le style cible est cohérent avec D3 (`to_cooklang`), dont `to_markdown` est le pendant « lisible humain ».
2. **AC2 — PUR / DÉTERMINISTE** : `to_markdown` est PURE (aucune I/O réseau, aucun fichier lu/écrit, aucun LLM, aucun `random`, aucune horloge). **Déterminisme** : même `recipe` → **exactement le même Markdown** sur N exécutions. Le formatage des nombres est déterministe (`2.0` → `2`, `2.5` → `2.5`), via un helper recopié du style D3 (`_format_number`/`format(.., "g")`) — **pas** d'import de `app/generator/cooklang.py` (autre story, lecture seule : on **recopie** le helper, on ne couple pas).
3. **AC3 — Étiquettes de sécurité VISIBLES (vitrine de l'explicabilité, archi §9.2/§6.1)** : les températures portées par les étapes (`Step.temperatures`, type `Temperature{value, unit, label}`) sont restituées de façon **VISIBLE** dans le rendu, **avec leur étiquette** `[SÉCURITÉ]` / `[TECHNIQUE]` / `[PRÉFÉRENCE]` (issue de `Temperature.label`, étiquetage barrière 1) et leur valeur + unité lisible (ex. « 74 °C **[SÉCURITÉ]** »). En particulier, les **températures de sécurité des protéines** (label « SÉCURITÉ ») apparaissent **clairement** dans la préparation (et/ou un rappel dédié) — c'est l'exigence d'explicabilité §9.2. Les durées (`Step.durations`) et le cookware (`Step.cookware`) sont également restitués quand présents.
4. **AC4 — Rendu ROBUSTE (recette minimale, pas de section vide incohérente)** : `to_markdown` produit un Markdown **valide** même pour une recette **minimale** (sans `techniques`, sans `notes`, voire sans ingrédients/étapes) : pas de section vide « cassée » ou incohérente. **Décision par défaut (figée)** : une section optionnelle (`## Techniques`, `## Notes`) n'est émise **que si** elle a du contenu (`recipe.techniques` / `recipe.notes` non vides) ; les sections structurantes `## Ingrédients` / `## Préparation` sont **toujours** présentes mais affichent un libellé sobre cohérent si la collection est vide (ex. « _(aucun ingrédient)_ ») plutôt qu'un en-tête suivi du vide. Le titre et la ligne de portions sont toujours émis.
5. **AC5 — Signature à 1 paramètre conforme §4.4 (PAS de `scaling_notes`)** : `to_markdown` prend **EXACTEMENT un paramètre** `recipe` (signature prescrite archi §4.4 : `to_markdown(recipe) -> str`). **Décision par défaut (figée et documentée)** : contrairement à `to_cooklang(recipe, scaling_notes)` (D3), `to_markdown` **ne prend PAS** `scaling_notes` ; il **rend la recette telle quelle**. Si l'on souhaite refléter le scaling dans le Markdown, c'est la `StructuredRecipe` **passée** qui porte déjà les valeurs voulues (l'orchestrateur/E1 peut construire/adapter le `StructuredRecipe` post-scaling avant l'appel) — `to_markdown` reste à **1 paramètre**, conforme §4.4. Ce choix est documenté en docstring.
6. **AC6 — Règle inter-couches + suite verte 0 régression** : (a) **Règle inter-couches (archi §3.1)** — `markdown.py` importe `app.generator.models` (même couche 4, LECTURE SEULE) ; il **N'IMPORTE NI** `app/scaling/`, **NI** `app/knowledge/`, **NI** `app/epicure/` au runtime, **NI** `anthropic`, **NI** `app/generator/cooklang.py`/`validate.py`/`prompt.py`/`client.py` (autres modules de la couche : pas nécessaires ici ; le helper de formatage est **recopié**). Module PUR/déterministe. (b) `tests/test_markdown.py` **vert** ; suite complète : **baseline 149 passed / 1 skipped** → 149 + nouveaux, **0 régression**.

## Dev Notes

### Contrat de données consommé — `app/generator/models.py` (LECTURE SEULE, figé par D1)

`to_markdown` consomme le `StructuredRecipe` (contrat figé D1) **sans le redéfinir ni le modifier** :

- `StructuredRecipe{title: str, servings: int, ingredients: tuple[Quantity, ...], steps: tuple[Step, ...], techniques: tuple[str, ...], notes: tuple[str, ...]}` — `servings` = portions de **BASE** (le scaling s'applique APRÈS la rédaction, côté pipeline, archi §7 ; cf. AC5).
- `Quantity{name: str, amount: float, unit: str, fixed: bool}` — `name` = libellé FR affichable (ex. « huile d'olive »). Le champ `fixed` n'a **pas** d'impact visuel obligatoire dans le Markdown lisible (c'est un verrou `=` propre au `.cook` de D3) ; D4 peut l'ignorer pour le rendu humain (décision par défaut documentée) ou le signaler discrètement (optionnel).
- `Step{text: str, cookware: tuple[str, ...], temperatures: tuple[Temperature, ...], durations: tuple[Duration, ...], technique_id: str | None}`.
- `Temperature{value: float, unit: str, label: str}` — `label` ∈ {« SÉCURITÉ », « TECHNIQUE », « PRÉFÉRENCE »} (étiquetage barrière 1, archi §6.1) ; `unit` ∈ {« C », « F »} → rendu `°C`/`°F`.
- `Duration{value: float, unit: str}` — `unit` privilégie « minute ».

### Signature à 1 paramètre — décision par défaut figée (AC5)

- La signature **prescrite** par l'architecture est `to_markdown(recipe) -> str` (archi §4.4, ligne « `def to_markdown(recipe) -> str: ...  # D4 (rendu lisible)` »), à **1 paramètre**. C'est volontairement **différent** de `to_cooklang(recipe, scaling_notes)` (D3, 2 paramètres) : le rendu lisible reflète la recette **telle qu'elle est passée**.
- **Décision par défaut (mode non-interactif)** : `to_markdown(recipe)` rend la `StructuredRecipe` reçue, sans paramètre de scaling. Si l'orchestrateur/E1 veut un Markdown **scalé**, il construit/adapte la `StructuredRecipe` (quantités scalées) **avant** l'appel, et la passe à `to_markdown`. Cela : (a) respecte §4.4 (1 paramètre) ; (b) garde D4 pur/déterministe et découplé de la couche 3 (aucun `scaling_notes` ⇒ aucune tentation d'importer/duck-typer `app/scaling/`). Le choix est documenté en docstring du module et de la fonction.

### Explicabilité : le rendu lisible est la VITRINE (AC3, archi §9.2/§6.1)

- Le Markdown est ce que **lit l'humain** : il doit rendre l'explicabilité **visible**. Les températures de **sécurité des protéines** (label « SÉCURITÉ ») et leurs étiquettes `[SÉCURITÉ]/[TECHNIQUE]/[PRÉFÉRENCE]` doivent apparaître **clairement** (c'est l'exigence d'explicabilité §9.2 ; l'étiquetage est posé en barrière 1, §6.1, et porté par `Temperature.label`).
- D4 **ne recalcule rien** et **n'invente rien** (FR3) : il restitue lisiblement ce que la `StructuredRecipe` (sortie LLM validée par D2) contient déjà (textes étiquetés, températures, durées, cookware). Les étiquettes gardent la **graphie accentuée** du contrat D1 / corpus S0.6.

### Robustesse / sections optionnelles (AC4)

- **Sections structurantes toujours présentes** : titre, ligne de portions, `## Ingrédients`, `## Préparation`. Pour une collection vide, afficher un libellé sobre (`_(aucun ingrédient)_` / `_(aucune étape)_`) plutôt qu'un en-tête suivi du vide (évite la « section vide cassée »).
- **Sections optionnelles conditionnelles** : `## Techniques` et `## Notes` ne sont émises **que si** `recipe.techniques` / `recipe.notes` sont non vides (décision par défaut figée). Cela garantit qu'une recette minimale produit un Markdown propre, sans en-tête orphelin.
- **Formatage des nombres déterministe** : `_format_number` (recopié du style D3) garantit `2.0 → "2"`, `2.5 → "2.5"`, stable cross-plateforme (`format(.., "g")`). Aucune dépendance à la locale.
