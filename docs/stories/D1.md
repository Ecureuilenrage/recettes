## Story

En tant que **développeur de la couche 4 (générateur LLM, `app/generator/`)**,
je veux **(a) figer un CONTRAT de données partagé `app/generator/models.py` (dataclasses stdlib `frozen`), (b) une fonction PURE et déterministe `build_prompt(req, neighbors, techniques, safety, forbidden) -> ConstrainedPrompt` (module `app/generator/prompt.py`) qui assemble le prompt système+utilisateur en reprenant VERBATIM les `llmConstraints` de la cuisine et l'étiquetage `[SÉCURITÉ]/[TECHNIQUE]/[PRÉFÉRENCE]`, et en injectant les 4 blocs autorisés (associations validées couche 1, techniques + `parameters` couche 2, lignes de sécurité, `#cookware` interdits), et (c) un point d'intégration `generate_recipe(prompt, complete=..., validate=None, max_retries=1) -> StructuredRecipe` (module `app/generator/client.py`) où `anthropic` est l'UNIQUE dépendance importée de façon GARDÉE, avec une couture INJECTABLE (`complete`) pour tester sans réseau ni clé et une boucle rejet→retry (1 max) pilotée par un `validate` injecté**,
afin de **réaliser la Barrière 1 du garde-fou anti-hallucination (archi §6.1 : le LLM CHOISIT dans la base, n'invente rien) et de fournir le SEUL point non-déterministe de la couche 4 sous une forme testable et découplée, en gelant les contrats que D2 (validation), D3 (émission `.cook`) et D4 (Markdown) consommeront sans les redéfinir**.

C'est la source de vérité importée en LECTURE SEULE par D2/D3/D4 (`from app.generator.models import StructuredRecipe, ...`).
2. **AC2 — `build_prompt` pur + déterministe, contraintes VERBATIM + 4 blocs** : `build_prompt(req, neighbors, techniques, safety, forbidden) -> ConstrainedPrompt` est PURE (aucune I/O réseau, aucun LLM, aucun `random`, aucun appel horloge). Le prompt système reprend **VERBATIM** les 5 `llmConstraints` de `cuisine-italienne.json` (cf. Dev Notes) et impose l'étiquetage `[SÉCURITÉ]/[TECHNIQUE]/[PRÉFÉRENCE]` de chaque consigne. Le prompt injecte les **4 blocs autorisés** (archi §6.1) : (1) associations validées (les `KeptNeighbor.name`/`score` de la couche 1) ; (2) techniques autorisées avec leurs `parameters` (couche 2, `Technique`) ; (3) lignes de sécurité applicables (`SafetyStandard` : protéine, min interne °C/°F, repos) ; (4) liste des `#cookware` interdits (`forbidden`). Le `ConstrainedPrompt` retourné renseigne `system`, `user`, et — pour la traçabilité/validation aval — `allowed_temperatures` (frozenset des valeurs numériques extraites des `parameters` techniques + des minima sécurité), `allowed_cookware` (ustensiles requis des techniques retenues, normalisés) et `forbidden_cookware` (= `forbidden`).
3. **AC3 — `generate_recipe` avec couture injectable (test SANS réseau)** : `generate_recipe(prompt, complete=..., validate=None, max_retries=1) -> StructuredRecipe`. `complete` est un callable injectable qui reçoit le `ConstrainedPrompt` (ou ses champs) et renvoie la sortie LLM (dict/JSON structuré — décision D10) ; en test on injecte un FAUX `complete` (aucun appel API réel). La sortie JSON est parsée en `StructuredRecipe` via un helper de parsing dédié (`parse_structured_recipe` dans `models.py` ou `client.py`). Un test prouve que `generate_recipe(prompt, complete=fake)` renvoie un `StructuredRecipe` correct **sans clé ni réseau**.
4. **AC4 — Boucle retry (1 max) via `validate` injecté + échec propre** : si `validate` (callable optionnel injecté) est fourni et renvoie un `ValidationResult` avec `ok=False`, `generate_recipe` relance `complete` UNE fois (`max_retries=1` par défaut) en passant le `feedback` ciblé du `ValidationResult` (au prompt utilisateur, sans muter le `ConstrainedPrompt` figé). Si la 2ᵉ tentative échoue encore → **échec propre** (exception claire en français, cohérent archi §6.2/§9.1 `502`/`500`). `validate=None` (défaut) ⇒ aucune validation, une seule génération. Un test injecte un `validate` qui rejette puis accepte (prouve le retry réussi) et un autre qui rejette toujours (prouve l'échec propre après 1 retry). **L'injection de `validate` ÉVITE que D1 importe D2** (découplage : le câblage réel de `validate_recipe` se fera côté E1/orchestrateur).
5. **AC5 — Import gardé d'`anthropic` UNIQUEMENT dans `client.py` + aucun import inter-couches runtime** : `anthropic` est importé de façon GARDÉE (`try: import anthropic except ImportError: anthropic = None`) et **UNIQUEMENT** dans `app/generator/client.py` (jamais dans `models.py`/`prompt.py`, qui restent purs). `app/generator/` n'importe AU RUNTIME NI `app/epicure/`, NI `app/knowledge/`, NI `app/scaling/` (les sorties des couches 1/2/3 arrivent EN PARAMÈTRES) ; les annotations de type vers ces couches passent par `if TYPE_CHECKING:` uniquement. Vérifiable par inspection des imports.
6. **AC6 — Déterminisme de `build_prompt` + suite verte 0 régression** : (a) **déterminisme** — `build_prompt(...)` avec les mêmes entrées produit un `ConstrainedPrompt` identique (mêmes `system`/`user`/frozensets) sur N exécutions (module pur, aucun `random`, aucune I/O). (b) `tests/test_prompt.py` et `tests/test_client.py` **verts** sans appel API réel ; un éventuel test d'intégration réel est marqué `@pytest.mark.skipif(not os.getenv("ANTHROPIC_API_KEY"), ...)`. (c) Suite complète : **baseline 93 passed** → 93 + nouveaux tests, **0 régression**.

@dataclass(frozen=True)

@dataclass(frozen=True)

    violations: tuple[Violation, ...] = ()

### Les 4 blocs injectés par `build_prompt` (archi §6.1)

Le LLM reçoit **uniquement** ces 4 blocs et CHOISIT dedans (FR3) :
1. **Associations validées (couche 1)** : les voisins retenus produits par `filter_neighbors(...)` — `FilteredNeighbors.kept: list[KeptNeighbor]`, chaque `KeptNeighbor{name, score, cuisine_context}`. `build_prompt` reçoit ces voisins EN PARAMÈTRE (`neighbors`). Décision par défaut : accepter soit un `FilteredNeighbors`, soit directement une séquence de `KeptNeighbor` / de tuples `(name, score)` (adapter au plus simple ; documenter). Injecter les noms (et scores en debug).
2. **Techniques autorisées + `parameters` (couche 2)** : la liste `list[Technique]` produite par `techniques_for(cuisine, hero, constraints)` (déjà filtrée des techniques à ustensile interdit). ### `generate_recipe` — couture injectable + retry (archi §6.2, §12 D9/D10)

- **Couture injectable `complete`** : `generate_recipe(prompt, complete=..., validate=None, max_retries=1)`. `complete` est un callable qui reçoit le prompt et renvoie la sortie LLM structurée (dict/JSON, D10). En PROD, défaut = `_default_complete` (appel Anthropic gardé). En TEST, on injecte un faux `complete` (aucun réseau, aucune clé). C'est le SEUL point non-déterministe de la couche 4 — isolé et testable (archi §6.3, R7 : pas d'appel LLM dans les tests unitaires).
- **Sortie structurée JSON (D10)** : la recette est demandée en JSON structuré (tool-use / structured output Anthropic) pour que la validation (§6.2) et le scaling (§5) s'appliquent mécaniquement avant l'émission `.cook` (D3). Le parsing JSON→`StructuredRecipe` passe par `parse_structured_recipe`.
- **Politique de violation = rejet + 1 retry (D9, archi §6.2 point 5)** : si `validate` (injecté) renvoie `ok=False`, relancer `complete` UNE fois avec le `feedback` ciblé, puis échec propre (exception claire FR → l'API web traduira en `502`/`500`, archi §9.1). Pas de « réparation » silencieuse. `max_retries=1` par défaut (coût/latence maîtrisés, NFR coût, R7).
- **Découplage D1 ⟂ D2** : `validate` est INJECTÉ (callable), pas importé. D1 ne connaît PAS `validate_recipe` (D2) : il consomme un callable conforme à `(StructuredRecipe) -> ValidationResult`. Le câblage réel `validate=validate_recipe` se fait côté E1/orchestrateur. Cela respecte la règle inter-couches ET le séquencement du sprint (D1 livré AVANT D2).
