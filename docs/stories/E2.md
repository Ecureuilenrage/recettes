## Story

En tant que **utilisateur du projet (vitrine portfolio)**,
je veux **une UI minimale Jinja2 (étendant `app/main.py`) : une page formulaire (`GET /`) pour saisir héros / cuisine / contraintes / portions / modèle, et une page résultat (`POST /generate-ui`) qui affiche la recette générée (`.cook` + Markdown) ET un panneau debug structuré en 4 sections (epicure / scaling / techniques / validation)**,
afin de **réaliser l'UI minimale décrite à l'archi §9.2 (formulaire → rendu recette + panneau debug = les 4 sections de `DebugInfo`), en RÉUTILISANT le pipeline E1 (`run_pipeline`) sans le réécrire, et de fournir la VITRINE portfolio de l'explicabilité (les voisins retenus/rejetés, le raisonnement de scaling par ingrédient, les techniques retenues/exclues et le résultat du garde-fou de sécurité, clairement présentés à l'humain)**.

## Acceptance Criteria

1. **AC1 — Page formulaire (`GET /`)** : une route `GET /` rend `templates/index.html` — un formulaire (méthode POST vers `/generate-ui`) avec les champs : **héros** (texte, requis), **cuisine** (défaut `italian_savory_v1`, `<select>`), **contraintes** (régime, sans-matériel ex. `pas_de_four`, mettre-en-avant — champs texte simples), **portions** (nombre, défaut 4), **modèle** (cooc/core, optionnel). La page utilise `fastapi.templating.Jinja2Templates(directory="templates")` avec un chemin ROBUSTE (relatif au module, indépendant du cwd). `GET /` -> 200 et la page contient le formulaire (`<form`, `name="hero"`, `name="servings"`, `name="cuisine"`).
2. **AC2 — Soumission (`POST /generate-ui`) -> rendu recette + panneau debug** : la route lit le form (dépend de `python-multipart`), construit un `GenerationRequest`, appelle `run_pipeline(request, complete=<get_complete>, index=<get_index>)` (RÉUTILISE les coutures d'injection E1 pour rester testable offline), puis rend `templates/result.html` avec : le **`.cook`** (bloc `<pre>`), le **Markdown** (zone lisible / `<pre>`), et le **panneau debug** présentant les **4 sections** de `DebugInfo` : **epicure** (voisins retenus/rejetés + raisons), **scaling** (par ingrédient : type, coefficient, formule, raisonnement, valeur), **techniques** (retenues/exclues + outil interdit/contrainte), **validation** (ok/violations). POST avec faux deps injectés -> 200, la page contient le `.cook`, le Markdown et les libellés des 4 sections.
3. **AC3 — Gestion d'erreur lisible dans l'UI (pas de crash)** : en cas d'erreur pipeline, l'UI affiche un message d'erreur clair SANS faire planter la page : `PipelineInputError` -> message « Entrée invalide (422) … » ; `PipelineGenerationError` -> message « Échec de génération (502) … ». La page d'erreur conserve la saisie du formulaire et n'affiche pas de recette. (HTTP 200 avec contenu d'erreur, pas une 500 brute.)
4. **AC4 — Helper PUR testable SANS jinja2/HTTP (`build_view_context`)** : une fonction `build_view_context(result, *, form=None, error=None) -> dict` transforme une `GenerationResponse` (ou un message d'erreur) en **dict de contexte** pour le template (cooklang, markdown, les 4 sections debug aplaties, libellés FR des sections, état `ok`/`error`, saisie `form`). Elle est PURE (aucune I/O réseau, aucun fichier, aucun LLM) et testable SANS fastapi/jinja2. Les templates ne portent QUE de la présentation (aucune logique métier).
5. **AC5 — Imports GARDÉS fastapi/jinja2 + testabilité (R7)** : les imports `fastapi`/`fastapi.templating.Jinja2Templates` dans `app/main.py` restent GARDÉS (patron existant E1) — si absents, l'app web/UI n'est pas construite mais `run_pipeline` ET `build_view_context` restent importables/testables. `tests/test_ui.py` : les tests TestClient/HTTP (GET `/`, POST formulaire, /health, /generate) sont GARDÉS par `pytest.importorskip("fastapi")` (et `jinja2`) -> skip propre si absents. Le test du helper `build_view_context` tourne SANS fastapi/jinja2 (offline, `GenerationResponse`/`DebugInfo` fabriqués à la main). AUCUN appel LLM/réseau/clé : les tests POST injectent un faux `complete`+`index` via `app.dependency_overrides` (patron `test_main.py`).
6. **AC6 — Non-régression E1 + suite verte** : `GET /health` et `POST /generate` (JSON E1) restent INTACTS et fonctionnels ; `run_pipeline` et les schémas/exceptions E1 sont INCHANGÉS. `tests/test_ui.py` vert ; suite complète : **baseline 194 passed / 3 skipped** -> 194 + nouveaux tests offline, **0 régression** (notamment AUCUNE régression sur `tests/test_main.py`). Si fastapi/jinja2 absents, les tests UI HTTP skippent proprement (attendu, documenté).

### Forme des 4 sections de `DebugInfo` (panneau debug = vitrine §9.2)

Aplaties telles quelles par `build_view_context` (aucun recalcul) :

- `epicure` = `{"kept": [{name, score, cuisine_context}], "rejected": [{name, score, reason}]}` (issu de `FilteredNeighbors.to_debug()`).
- `scaling` = `[{name, type, coeff, formula, reasoning, value}]` (un dict par ingrédient).
- `techniques` = `{"kept": [technique_id...], "excluded": [{technique_id, forbidden_tool, via_constraint}]}`.
- `validation` = `{"ok": bool, "violations": [{kind, detail, severity}], "feedback": str}`.

### Décisions par défaut (mode non-interactif)

- **Route de soumission = `POST /generate-ui`** (et non `POST /`) : évite toute collision/ambiguïté avec l'endpoint JSON `POST /generate` (E1, intact) et garde une URL HTML distincte de l'API. `GET /` = page formulaire.
- **Chemin des templates ROBUSTE** : `Jinja2Templates(directory=<repo>/templates)` calculé via `os.path.dirname(os.path.abspath(__file__))` (indépendant du cwd) — décision documentée.
- **Champs « liste » du formulaire** (`diet`, `no_cookware`) saisis en texte, séparés par virgule ou saut de ligne, découpés côté glu (`_request_from_form`). `highlight` vide -> `None`. La VALIDATION métier (héros hors vocab, cuisine inconnue) reste déléguée à `run_pipeline` (E2 n'ajoute aucune logique métier).
- **Cuisine en `<select>`** avec l'unique cuisine disponible (`italian_savory_v1`) + `model` en `<select>` (cooc/core). Portions par défaut 4.
- **`.cook` et Markdown rendus dans des `<pre>`** (présentation lisible et fidèle). Le Markdown est affiché tel quel (pas de rendu HTML Markdown — décision sobre v1, évite une dépendance ; le `<pre>` reste lisible).
- **Gestion d'erreur dans la page** (AC3) : on RETOURNE une page 200 avec un message lisible plutôt qu'une 422/502 HTTP brute, car l'UI est destinée à l'humain (les codes HTTP restent portés par l'API JSON E1). Décision documentée.
- **Signature `TemplateResponse(request, name, context)`** : la convention historique `TemplateResponse(name, {"request": ...})` a été retirée des versions récentes de Starlette (constaté empiriquement : `TypeError: unhashable type: 'dict'`). On utilise la signature moderne (request en 1er argument positionnel).
  [Source : docs/architecture.md#9.2 ; consignes mode non-interactif ; vérification empirique Starlette 1.2.x]
