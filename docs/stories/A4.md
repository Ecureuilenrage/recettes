## Story

En tant que **développeur de la couche 1 Epicure (associations)**,
je veux **une fonction pure `translate(term: str) -> str` (module `app/epicure/translate.py`) qui traduit un nom d'ingrédient français usuel (ex. « huile d'olive », « basilic », « poivre noir ») vers la clé Epicure `snake_case` anglaise correspondante (ex. `olive_oil`, `basil`, `black_pepper`), via une table de correspondance versionnée `app/epicure/fr_aliases.json` et une normalisation robuste de la saisie (minuscule, accents, apostrophe)**,
afin de **faire le pont entre le héros saisi en français par l'utilisateur (FR) et le vocabulaire Epicure en anglais (`EpicureIndex.vocab`, 1790 entrées `snake_case` EN), pour que `neighbors(hero, k)` reçoive une clé valide et ne lève pas `KeyError` à tort (R4 / archi §9.1), et lever ainsi la réserve RZ3 préalable à E1/E2**.

## Acceptance Criteria

1. **AC1 — Module `translate` + table `fr_aliases.json`** : `app/epicure/translate.py` expose `translate(term: str) -> str` qui retourne la clé Epicure `snake_case` EN d'un terme FR, **et** `translate_many(terms: Iterable[str]) -> list[str]` (mapping ordonné, même politique d'erreur par terme). La table de correspondance vit dans `app/epicure/fr_aliases.json` (objet JSON `{ alias_FR_normalisé : clé_Epicure }`, valeurs `snake_case` EN). Le JSON est chargé **une seule fois** (lecture seule, `functools.lru_cache`). Plusieurs alias FR peuvent pointer vers une même clé (ex. `spaghetti`, `penne`, `pates courtes` → `pasta`).
2. **AC2 — Corpus italien couvert (assertions chiffrées)** : la table couvre **au minimum** le noyau d'ingrédients du corpus S0.6 (les 13 recettes `recipes/*.cook`). Vérifications chiffrées explicites : `translate("huile d'olive") == "olive_oil"`, `translate("ail") == "garlic"`, `translate("basilic") == "basil"`, `translate("poivre noir") == "black_pepper"`, `translate("parmesan râpé") == "parmesan_cheese"`, `translate("guanciale") == "pancetta"`. Le test asserte aussi que **les ≥ 38 clés cibles du noyau** (table de référence ci-dessous) sont toutes produites par au moins un alias. La table est par nature **À COMPLÉTER** (extensibilité), mais ce noyau + le fallback honnête (AC4) **suffisent à lever RZ3 pour la v1**.
3. **AC3 — Normalisation de la saisie (minuscule / accents / apostrophe / espaces)** : le lookup se fait sur la **forme normalisée** du terme et des alias (minuscule + suppression des accents NFKD + normalisation de l'apostrophe/élision + espaces multiples réduits). Vérifications : `translate("Huile d'Olive") == translate("huile d'olive") == "olive_oil"` (casse + apostrophe typographique « ' » ⇔ « ' »), `translate("BASILIC") == "basil"`, `translate("  câpres  ") == "caper"` (espaces, accents). La forme normalisée d'un alias est calculée à la **construction de l'index** (pas de mutation du JSON source).
4. **AC4 — Fallback explicite (terme absent du vocab) — cf. R4 / archi §9.1** : si le terme FR n'a **aucune** correspondance dans `fr_aliases.json`, `translate` **lève `KeyError`** avec un **message clair en français** (ex. `« Ingrédient inconnu du vocabulaire FR→Epicure : <terme> (à ajouter dans fr_aliases.json) »`). C'est le comportement **cohérent** avec `EpicureIndex.neighbors` (`app/epicure/loader.py`) qui lève déjà `KeyError` sur ingrédient absent, et qui alimente le `422` explicite de l'API (archi §9.1). Le **contrat principal reste `KeyError`** ; une variante non-levante explicite (`translate(term, default=...)` ou `try_translate(term) -> str | None`) est **autorisée mais optionnelle**, à documenter si livrée.
5. **AC5 — Déterminisme + intégrité table↔vocab + suite verte** : (a) **déterminisme** — même terme → même clé sur N exécutions (module pur, aucun `random`, aucune I/O hors lecture du JSON). (b) **Intégrité (filet anti-typo)** — un test **gardé par l'existence de `docs/epicure/vocab.csv`** vérifie que **toutes les valeurs** de `fr_aliases.json` existent bien comme clés (colonne `name`) dans `vocab.csv` ; si le fichier est absent → **`pytest.skip` propre**. (c) `tests/test_translate.py` **vert** **sans régression** sur la suite complète (cible : **68 tests** → 68 + nouveaux, 0 régression).

### Stratégie de normalisation (réutiliser le patron `app/scaling/table.py`)

Le lookup FR→Epicure est tolérant casse/accents/apostrophe. Réutiliser la stratégie éprouvée (C1) :
1. **Normaliser l'apostrophe/élision** : remplacer l'apostrophe typographique « ' » (U+2019) par l'apostrophe droite « ' » (U+0027), réduire les espaces multiples, `strip()`. Ceci AVANT l'étape accents/casse.
2. **Supprimer les accents** : `unicodedata.normalize("NFKD", s)` puis suppression des marques combinantes (`unicodedata.combining`) — patron `_strip_accents` de `app/scaling/table.py:52-55`.
3. **Minuscule** : `lower()` — patron `_normalize` de `app/scaling/table.py:58-60`.
4. **Indexer** : l'index de lookup `{ _normalize_term(alias) : clé }` est construit **une fois** au chargement (`lru_cache`). Le JSON source garde les alias **lisibles** (avec accents/apostrophe) ; la normalisation est appliquée des **deux côtés** (alias ET terme saisi) au moment du lookup.
5. **Ne PAS importer `app/scaling/` ni `app/knowledge/`** : les couches sont indépendantes (archi §3.1, dépendances unidirectionnelles `main → {1,2,3,4}`, les couches ne s'importent pas entre elles). **Recopier** le helper de normalisation dans `app/epicure/translate.py` (≈ 10-12 lignes stdlib). Cette légère duplication est volontaire et préférable à un couplage inter-couches (même choix qu'en B3/B4).
  [Source : app/scaling/table.py#_strip_accents,#_normalize (52-60) ; app/knowledge/loader.py (mêmes helpers recopiés, 61-86) ; docs/architecture.md#3.1 (règle de dépendances unidirectionnelles, les couches ne se connaissent pas)]

> **Note tokenisation** : contrairement à C1/B4 (matching d'ustensiles/ingrédients dans des libellés multi-mots), A4 fait un **lookup exact** sur la forme normalisée complète du terme (l'alias entier est la clé). `_tokenize` n'est donc **pas requis** pour le contrat principal ; seuls `_strip_accents`/`_normalize` + la normalisation apostrophe/espaces sont recopiés. Si une tolérance par token s'avère utile plus tard (ex. ordre des mots), elle relèvera d'une story d'extension, pas d'A4.
