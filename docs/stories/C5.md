## Story

En tant que **développeur du moteur de scaling (couche 3)**,
je veux **une suite de tests `pytest` déterministe et complète (les 4 stubs implémentés + les cas C2/C3/C4, un test de déterminisme N exécutions, et les scénarios ×2/÷2/×4) ainsi qu'un notebook de calibration amorcé (moteur vs ×N naïf)**,
afin de **prouver que le cœur de scaling est correct et reproductible (OA1, NFR déterminisme), et d'outiller la future calibration des coefficients (F2) sans modifier le code**.

## Acceptance Criteria

1. **AC1 — `pytest` vert sans skip** : `pytest tests/test_scaling.py` passe **sans aucun `skip`**. Les **4 stubs** existants (`test_sel_sous_lineaire`, `test_oeufs_discrets`, `test_temps_geometrique`, `test_temperature_figee`) sont **implémentés** (plus de corps `...`), et les cas couvrant C2/C3/C4 sont ajoutés : œufs discrets (`scale_eggs(3,2.0)→5`, `scale_eggs(2,1.5)→3`), temps géométrique (`scale_time(20,2.0)≈32`), flag de non-linéarité + réserve 10 % du sel.
2. **AC2 — Déterminisme (N exécutions)** : un test asserte qu'une **même entrée** produit un `ScaledQuantity` **identique** sur **N exécutions** (N ≥ 100). Égalité sur les champs porteurs de sens (`name`, `value`, `unit`, `type`, `fixed`, `notes`, `reserve`) — pas seulement l'identité d'objet. S'applique aussi à `scale_eggs` / `scale_time`.
3. **AC3 — Scénarios ×2, ÷2, ×4** : pour des ingrédients **représentatifs** (linéaire : `tomate` ; sous-linéaire : `sel` ; figé : température ; discret : `oeuf` ; géométrique : `temps`), des assertions chiffrées couvrent `k=2.0`, `k=0.5` et `k=4.0`. Notamment : monotonie attendue (k↑ ⇒ valeur↑ pour linear/sublinear), `k=0.5` réduit la quantité, `fixed` reste inchangé à tout `k`.
4. **AC4 — Notebook amorcé** : `notebooks/calibration_scaling.ipynb` existe, s'exécute de bout en bout sans erreur, et **compare le moteur au ×N naïf** (multiplication linéaire de toutes les quantités) sur quelques ingrédients représentatifs (table affichant `qty_base`, `×N_naïf`, `moteur`, `écart`). Une cellule Markdown documente que la comparaison sur **corpus réel** (10-15 recettes italiennes) se complète après **S0.6** et alimentera la calibration **F2**.

## Dev Notes

### Contexte architectural (à respecter impérativement)

- **Contrat de pureté / déterminisme (OA1, archi §5.1, §11)** : `app/scaling/` est **pur et déterministe** — même `(name, qty, unit, k)` → **exactement** le même `ScaledQuantity`. C'est ce contrat que C5 **prouve** par les tests (déterminisme N exécutions, ×2/÷2/×4). Les tests ne doivent introduire **aucun** I/O autre que la lecture de la table (déjà faite par le moteur), **aucun** appel LLM, **aucun** `random`.
  [Source : docs/architecture.md#5.1 ; #11 Principes — « le cœur est 100 % déterministe → couverture prioritaire »]
- **Coefficients en table, jamais en dur (D7)** : les tests **asservissent** les valeurs attendues aux coefficients de `docs/scaling/table-scaling-sale.json` (sel `0.75`, temps `exponent 0.6667`, œufs `grams_per_unit 50`). Ne **pas** dupliquer ces littéraux comme « valeurs magiques » non sourcées : commenter d'où vient chaque attendu (ex. `# 1 × 2.0^0.75 ≈ 1.6818, coeff sel table`). Le notebook **lit** la table via le moteur, ne la fige pas.
  [Source : docs/architecture.md#12 (D7) ; docs/scaling/table-scaling-sale.json#meta.disclaimer]
- **C5 = aboutissement de C1-C4** : C5 n'implémente **aucune** logique métier de scaling — il **teste** ce que C1 (`classify`/`scale` linear/sublinear/fixed), C2 (`scale_eggs`), C3 (`scale_time`), C4 (flags + réserve) ont livré. Si une API amont diffère de ce qui est décrit ci-dessous, **s'aligner sur l'implémentation réelle** de C1-C4 (lire `app/scaling/engine.py` et `table.py`) plutôt que d'inventer.
  [Source : docs/stories/sprint-status.yaml#C5.deps = [C1,C2,C3,C4,S0.6] ; docs/stories/C1.md]

### Valeurs attendues figées (depuis la table — pour les assertions)

| Cas | Entrée | Attendu | Provenance |
|---|---|---|---|
| sel (sublinear) | `scale("sel",1,"c.a.c",2.0)` | `≈ 1.68` (< 2) | `coeff 0.75` → `1×2^0.75` |
| tomate (linear, défaut) | `scale("tomate",200,"g",2.0)` | `400` | aucune catégorie ne matche → `linear` |

### Le notebook : moteur vs ×N naïf

- **But** (archi §11, ligne « Calibration scaling (moteur vs ×N naïf) ») : montrer **visuellement** que le moteur custom diverge du ×N naïf là où ça compte (sel, épices, temps) et l'égale ailleurs (linéaire). C'est l'outil de la boucle de calibration **F2** et la réponse au risque **R3** (« coefficients faux »).
- **×N naïf** = `qty × k` pour **toutes** les quantités (comportement Cooklang binaire, D6). Le « moteur » = sortie de `scale(...)`. La colonne `écart` = `moteur − ×N_naïf` (ou ratio).
- **Amorce vs complet** : en sprint 1, le notebook tourne sur une **petite liste codée en dur** d'ingrédients (pas besoin de S0.6). La version **complète** (boucle sur les 10-15 recettes `recipes/` issues de S0.6, comparaison ×2/÷2 avec cuisine réelle) est finalisée **après S0.6** (sprint 2). Documenter ce différé dans une cellule Markdown.
- Outil : `jupyter` (déjà dans `requirements.txt`, archi §3 « non épinglée »). Créer le `.ipynb` directement (JSON `nbformat` v4) ou via l'outil notebook ; le garder **léger** (pas de pandas obligatoire).

[Source : docs/architecture.md#3 (jupyter), #11 (ligne calibration), #13 R3 ; docs/scaling/table-scaling-sale.json#meta.disclaimer ; docs/recherche-ouverte.md §C (calibration)]
