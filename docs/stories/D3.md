## Story

En tant que **développeur de la couche 4 (générateur LLM, `app/generator/`)**,
je veux **une fonction PURE et déterministe `to_cooklang(recipe, scaling_notes) -> str` (module `app/generator/cooklang.py`) qui émet un document Cooklang `.cook` valide à partir d'un `StructuredRecipe` (contrat D1, consommé en LECTURE SEULE) et des sorties de scaling de la couche 3 (`ScaledQuantity`/`ScaledEggs`/`ScaledTime` + notes) reçues EN PARAMÈTRE (duck-typing), en posant le frontmatter `servings`, les marqueurs `@ingrédient{quantité%unité}` / `#ustensile` / `~{durée}`, les verrous `=` sur les quantités `fixed`, et les notes `--` (réserve 10 %, changement de contenant + étiquettes `[SÉCURITÉ]/[TECHNIQUE]/[PRÉFÉRENCE]`), AINSI QUE une fonction de validation regex légère `validate_cooklang(text) -> tuple[bool, list[str]]` (réutilisant le patron de `recipes/_check_cook.py`) qui vérifie la bonne formation du `.cook` émis**,
afin de **réaliser l'étape « Couche 4 (émission) » du pipeline (archi §7 : `to_cooklang(recipe, scaling_notes) → .cook`) qui reçoit les `ScaledQuantity`/notes du moteur (couche 3) APRÈS le scaling, et de RÉSOUDRE la réserve RZ5 en actant le fallback regex (décision D5/archi §8.4/§12 : templating maison + validation regex, PAS de binding natif ni de dépendance `cooklang-py`)**.

## Acceptance Criteria

1. **AC1 — `to_cooklang` émet un `.cook` bien formé (frontmatter + marqueurs)** : `to_cooklang(recipe, scaling_notes) -> str` produit un document Cooklang complet : (a) **frontmatter** `---\nservings: N\n---` où `N` = `recipe.servings` (portions de BASE, archi §7) ; (b) chaque `Step.text` rédigé, avec les marqueurs Cooklang **`@ingrédient{quantité%unité}`** pour les ingrédients, **`#ustensile`** pour le cookware (`Step.cookware`), **`~{durée}`** pour les timers (`Step.durations`). Le document émis **passe la validation regex** d'AC5 (frontmatter présent, ≥ 1 marqueur ingrédient bien formé, accolades équilibrées). Le style cible est celui des `.cook` réels du corpus S0.6 (cf. `recipes/04-spaghetti-alla-carbonara.cook`, `recipes/12-osso-buco-alla-milanese.cook`).
2. **AC2 — Quantités SCALÉES quand `scaling_notes` est fourni, sinon quantités de base (archi §7)** : `to_cooklang` reçoit `scaling_notes` (sorties de la couche 3) **EN PARAMÈTRE** et émet les quantités **scalées** lorsqu'elles sont disponibles, **alignées par nom d'ingrédient** avec `recipe.ingredients` (`Quantity.name`). Si aucune note de scaling ne correspond à un ingrédient (ou `scaling_notes is None`), l'émission utilise la quantité de **base** (`Quantity.amount`/`Quantity.unit`) de la recette. **Décision par défaut (figée)** : `scaling_notes` est accepté de façon **SOUPLE** par **duck-typing** — `None` (→ quantités de base), une **liste** de `ScaledQuantity` (alignée par `.name`), un **dict** `{name: ScaledQuantity}`, ou un objet exposant `.name`/`.value`/`.unit`/`.fixed`/`.notes`. **Aucun import** de `app/scaling/` : on lit les attributs attendus, on ne couple pas le type.
3. **AC3 — Verrous `=` sur les quantités `fixed`** : une quantité `fixed` (figée — température/quantité non scalée) reçoit le **verrou `=`** dans le marqueur Cooklang, format `@sel{=1%c.à.c}` (archi §8.4). La condition `fixed` est lue **soit** sur `Quantity.fixed=True` (contrat D1), **soit** sur `ScaledQuantity.fixed=True` (couche 3, prioritaire si une note de scaling correspond). Le verrou est aussi posé sur les **températures figées** émises sous forme de marqueur (ex. `(=100%°C)`, `@four{=163%°C}`) lorsque `to_cooklang` les matérialise depuis `Step.temperatures` (température = type `fixed`, archi §5.4).
4. **AC4 — Notes `--` (réserve, contenant, étiquettes)** : `to_cooklang` pose des notes Cooklang `--` issues : (a) des `scaling_notes` de la **couche 3** — note de **réserve 10 %** (`ScaledQuantity.notes`/`.reserve`, ex. « -- réserver ~10 % et ajuster en fin de cuisson ») et note de **changement de contenant** (`ScaledTime.notes`/`.note`, ex. « -- ne se double pas proprement au-delà de ~1.5–2× ») ; (b) des **étiquettes `[SÉCURITÉ]/[TECHNIQUE]/[PRÉFÉRENCE]`** portées par le LLM dans `Step.text`/`StructuredRecipe.notes`. Les notes déjà préfixées `--` ne sont **pas re-préfixées** (idempotence du marqueur). Les notes émises restent sur des lignes/segments bien formés (n'invalident pas la regex AC5).
5. **AC5 — `validate_cooklang(text) -> tuple[bool, list[str]]` (validation regex, RZ5)** : le module expose une **fonction de validation regex légère**, réutilisant le **patron de `recipes/_check_cook.py`** (regex RECOPIÉES, pas d'import), qui vérifie la bonne formation d'un texte `.cook` : (1) **frontmatter `servings`** présent (`RE_SERVINGS`) ; (2) **≥ 1 marqueur ingrédient** `@…{…%…}` (`RE_INGREDIENT` = `@[^@#~\n]+?\{[^}]*?%[^}]*?\}`) ; (3) **accolades `{}` équilibrées** (`text.count("{") == text.count("}")`) ; (4) marqueurs `#`/`~`/`=`/`--` bien formés (timers `~{…}` via `RE_TIMER`, cookware `#…` via `RE_COOKWARE` ; verrou `=` à l'intérieur d'accolades ; notes `--`). Retour : `(ok: bool, problems: list[str])` (`ok=True` ⇔ `problems == []`), messages en français. **AUCUNE dépendance `cooklang-py`** (RZ5 : identité/maintenance du paquet PyPI non confirmée → fallback regex ACTÉ, décision D5). La fonction est appelée par les tests d'AC d'AC1 et par un test non-tautologique (un `.cook` MAL formé est rejeté).
6. **AC6 — Pureté/déterminisme + règle inter-couches + suite verte 0 régression** : (a) **PURETÉ** — `to_cooklang`/`validate_cooklang` sont PURES (aucune I/O réseau, aucun LLM, aucun `random`, aucune horloge, aucun fichier lu/écrit) ; **déterminisme** — mêmes `(recipe, scaling_notes)` → **exactement le même texte** sur N exécutions. (b) **Règle inter-couches (archi §3.1)** — `cooklang.py` importe `app.generator.models` (même couche, LECTURE SEULE) ; il **N'IMPORTE NI** `app/scaling/`, **NI** `app/knowledge/`, **NI** `app/epicure/` au runtime, **NI** `anthropic`, **NI** `cooklang-py` ; `scaling_notes` arrive EN PARAMÈTRE (duck-typing) ; annotations vers la couche 3 → `if TYPE_CHECKING:` uniquement. (c) `tests/test_cooklang.py` **vert** ; suite complète : **baseline 111 passed / 1 skipped** → 111 + nouveaux, **0 régression**.

### Stratégie d'émission `.cook` (style corpus S0.6, archi §8.4)

Style cible observé dans `recipes/*.cook` (corpus S0.6, lecture seule) :

- **Frontmatter** : `---\nservings: 4\n---` en tête.
- **Ingrédient** : `@gros sel{30%g}`, `@spaghetti{400%g}`, `@oeufs{3%}` (unité vide tolérée). Avec verrou : la température figée s'écrit `(=100%°C)` ou rattachée à un ustensile `@four{=163%°C}` / `@four{=240%°C}` (cf. `12-osso-buco`).
- **Ustensile** : `#grande casserole`, `#poêle`, `#cocotte`, `#thermomètre`.
- **Timer** : `~{9%minutes}`, `~{135%minutes}`, `~{2%minutes}`.
- **Notes `--`** : en fin de segment ou en ligne, ex. `-- al dente, goûter.`, `-- [SÉCURITÉ] repos 3 min minimum…`, `-- [TECHNIQUE]…`, `-- [PRÉFÉRENCE]…`. Une ligne `--` peut aussi être autonome (cf. `04-carbonara` ligne 4 : `-- Technique : pasta_al_dente [TECHNIQUE]…`).

**Décision par défaut (figée)** sur la composition : le LLM (D1) produit déjà des `Step.text` étiquetés et potentiellement porteurs de marqueurs. `to_cooklang` privilégie l'**émission depuis les champs structurés** (`ingredients`, `Step.cookware`/`durations`/`temperatures`) pour garantir la bonne formation et le report des **quantités scalées**, et **n'invente rien** (FR3 : le texte/les valeurs viennent de la recette et des `scaling_notes`). Si `Step.text` contient déjà un marqueur formé pour un élément, on évite le doublon. La granularité exacte (réécriture vs annotation) est laissée à l'implémentation **du moment que le résultat passe `validate_cooklang`** et reste déterministe — la story fige le **contrat** (frontmatter + marqueurs + verrous + notes + validité regex), pas le micro-gabarit ligne à ligne.
