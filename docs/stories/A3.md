## Story

En tant que **développeur de la couche 1 (associations Epicure)**,
je veux **une fonction pure `filter_neighbors(candidates, cuisine, constraints) -> FilteredNeighbors` qui, à partir des voisins bruts produits par `EpicureIndex.neighbors(...)`, applique un filtrage à deux régimes : (1) un filtrage *cuisine SOUPLE* qui n'écarte aucun voisin mais l'ANNOTE de sa pertinence/contexte cuisine (via la macro-région résolue), et (2) un rejet *DUR* déterministe des voisins exclus par une contrainte de régime alimentaire (ex. « végétarien » écarte `chicken`), chaque rejet portant sa raison explicite**,
afin de **fournir au générateur LLM (couche 4) une liste d'associations déjà filtrées par les contraintes déterministes (FR2), tout en exposant retenus/rejetés + raisons au panneau debug (FR7) pour l'explicabilité — sans jamais lever d'exception même si les données cuisine optionnelles sont absentes**.

## Acceptance Criteria

1. **AC1 — Signature exacte + type de sortie** : `app/epicure/filter.py` expose `filter_neighbors(candidates: list[tuple[str, float]], cuisine: str, constraints: Constraints) -> FilteredNeighbors`, conforme à la signature **prescrite** (archi §4.1). `FilteredNeighbors` est une dataclass stdlib exposant **`kept`** (les voisins retenus, avec leur annotation cuisine) et **`rejected`** (liste de tuples **`(name: str, score: float, reason: str)`**). `candidates` reçoit des clés Epicure **déjà résolues** (snake_case EN, ex. `olive_oil`, `chicken`) — A3 n'effectue **aucune** traduction. `candidates` vide → `kept` et `rejected` vides (pas d'erreur).
2. **AC2 — Filtrage cuisine SOUPLE + dégradation gracieuse (D14)** : le filtrage cuisine ne **supprime jamais** un voisin. Chaque voisin retenu est **annoté** d'un contexte cuisine (ex. macro-région résolue de `cuisine` via `docs/epicure/cuisine_macroregions.json` : une `cuisine` contenant `ital` → tradition `Italian` → macro-région `Mediterranean`) ; l'annotation sert le debug FR7, pas la sélection. Si `cuisine_macroregions.json` (ou tout autre fichier cuisine optionnel) est **absent / non résoluble**, l'annotation devient **neutre/inconnue** (ex. `None` ou `"unknown"`), **aucune exception** n'est levée, et **aucun** voisin n'est supprimé. Test : avec ou sans données cuisine, `len(kept) + len(rejected) == len(candidates)` et aucun rejet n'a une raison de type « cuisine ».
3. **AC3 — Rejet DUR par régime alimentaire (déterministe)** : avec `constraints.diet == ["végétarien"]`, un voisin dont la clé est listée dans `app/epicure/diet_exclusions.json` pour ce régime (ex. `chicken`, `beef`, `fish`, `meat`…) est placé dans **`rejected`** avec une `reason` claire en français (ex. `"régime végétarien : ingrédient carné/poisson exclu"`) et **n'apparaît pas** dans `kept`. Sans contrainte de régime (`constraints.diet == []`), ce **même** voisin (`chicken`) reste dans **`kept`**. Le matching de régime est **insensible à la casse et aux accents** (« végétarien », « Vegetarien », « VÉGÉTARIEN » → même régime). Une clé de régime **inconnue** de `diet_exclusions.json` est un **no-op** (aucun rejet, pas d'erreur).
4. **AC4 — `rejected` exploitable par FR7 (`DebugInfo.epicure`)** : chaque entrée de `rejected` est un tuple `(name, score, reason)` directement sérialisable pour `DebugInfo.epicure` (archi §9.1, « voisins retenus/rejetés + raisons »). Le `score` est le score cosinus d'origine reçu en entrée (préservé, non recalculé). Une représentation sérialisable de l'ensemble (retenus annotés + rejetés avec raison) est disponible pour alimenter le panneau debug (ex. méthode/attribut `to_debug()` ou champs directement lisibles).
5. **AC5 — Déterminisme + tests verts sans régression** : `filter_neighbors` est **pure et déterministe** (mêmes entrées → même sortie ; ordre des `candidates` préservé). `tests/test_filter.py` couvre AC1–AC4 + déterminisme, en important **`app.epicure.filter` directement** (pas via `app.epicure.__init__`). Cible : `python -m pytest tests/test_filter.py -q` **vert**, et **`python -m pytest -q`** **vert sans régression** sur la suite existante (**68 tests**).
