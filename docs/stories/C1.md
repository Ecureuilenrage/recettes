## Story

En tant que **développeur du moteur de scaling (couche 3)**,
je veux **un classificateur d'ingrédients (`classify`) qui lit la table `table-scaling-sale.json` et une fonction `scale` couvrant les types `linear`, `sublinear` et `fixed`**,
afin de **poser les fondations pures et déterministes du cœur de scaling, sur lesquelles s'appuieront ensuite les œufs (C2), le temps géométrique (C3) et les flags/réserves (C4)**.

## Acceptance Criteria

1. **AC1 — Lecture de la table** : `classify(name)` lit `docs/scaling/table-scaling-sale.json` (chargée **une seule fois**, en **lecture seule**). Si aucune catégorie ne correspond, le type par défaut est `linear` (`defaults.main_ingredients`).
2. **AC2 — Matching robuste** : le matching se fait par **token entier**, **insensible à la casse et aux accents** (pas de sous-chaîne). Ex. : « ail » ne doit pas matcher « vol-au-vent ».
3. **AC3 — Sous-linéaire (sel)** : `scale("sel", 1, "c.à.c", 2.0)` retourne une valeur **< 2** (type `sublinear`, coeff `0.75` → `1 × 2.0^0.75 ≈ 1.68`).
4. **AC4 — Linéaire par défaut** : `scale("tomate", 200, "g", 2.0)` retourne **400 g** (type `linear` par défaut, aucune catégorie ne matchant « tomate »).
5. **AC5 — Figé (température)** : un nom de type température (« température », « four », « feu »…) est classé `fixed` ; sa valeur reste **inchangée**, destinée au verrou `=` Cooklang. Ex. : `scale("four", 180, "°C", 2.0)` → valeur `180`, `fixed=True`.
6. **AC6 — Sortie structurée** : `scale(...)` retourne un `ScaledQuantity` exposant **au minimum** : `name`, `value`, `unit`, `type`, `fixed`, `notes`, `debug`.

## Dev Notes

### Contexte architectural (à respecter impérativement)

- **Contrat de pureté (OA1, archi §5.1)** : `app/scaling/` est **pur et déterministe** — aucun I/O réseau, aucun LLM, aucun état mutable global. Seule lecture admise : la table JSON, chargée **une fois** en lecture seule. Même `(name, qty, unit, k)` → **exactement** le même `ScaledQuantity`. C'est ce contrat qui rend le cœur testable (C5).
  [Source : docs/architecture.md#5.1-Contrat-de-pureté]
- **Aucun coefficient codé en dur (D7, DoD C1)** : **tous** les coefficients, exposants et flags proviennent de `table-scaling-sale.json`. Le module la **lit**, ne la **fige** pas. La calibration (F2) modifiera la table, jamais le code. Un coeff `0.75` littéral dans `engine.py`/`table.py` est une violation directe de la DoD.
  [Source : docs/architecture.md#12-Décisions-techniques-clés (D7) ; docs/scaling/table-scaling-sale.json#meta.disclaimer]
- **Les cinq types de scaling** (archi §5.2, depuis `meta.scalingTypes`) : `linear` (`qty*k`), `sublinear` (`qty*k^coeff`, 0<coeff<1), `discrete` (œufs, C2), `geometric` (temps `k^(2/3)`, C3), `fixed` (inchangé → `=` Cooklang). **C1 ne couvre que `linear`, `sublinear`, `fixed`** ; `discrete`/`geometric` sont livrés en C2/C3.
  [Source : docs/architecture.md#5.2 ; docs/scaling/table-scaling-sale.json#meta.scalingTypes]

### Source de vérité — `docs/scaling/table-scaling-sale.json`

Structure (déjà présente, ne pas modifier) :
- `meta.scalingTypes` : définitions des 5 types.
- `defaults.main_ingredients` : `{ "type": "linear", ... }` → **fallback** de `classify`.
- `categories[]` : chaque entrée porte `match` (liste de mots-clés FR + EN), `type`, et selon le type : `coeff` (sublinear), `reserve_pct` (sel), `nonlinearFlag` (piment, temps), `grams_per_unit`/`tbsp_per_unit`/`round` (œufs), `exponent` (temps), `reason`.
- `rules[]`, `geometricTimeExamples` : utiles pour C3/C4, pas requis en C1.

Catégories pertinentes pour les AC de C1 :
- **sel** : `{ "match": ["sel","salt","sauce soja","soy sauce"], "type":"sublinear", "coeff":0.75, "reserve_pct":10 }` → `1 × 2.0^0.75 ≈ 1.6818` (AC3, < 2). Note : `reserve_pct` est **lu** mais **non appliqué** en C1 (réserve 10 % = C4).
- **température** : `{ "match": ["temperature","four","feu","oven","heat"], "type":"fixed" }` → AC5.
- **tomate** : **absente** des `categories` → `classify` retourne le défaut `linear` → AC4.

[Source : docs/scaling/table-scaling-sale.json ; docs/architecture.md#5.3, #5.4]

### Signatures prescrites (archi §4.3 — ne pas dévier)

```python
def classify(name: str) -> ScalingRule: ...                 # lit la table, retourne type/coeff
def scale(name: str, qty: float, unit: str, k: float) -> ScaledQuantity: ...
```

Structure de sortie attendue (archi §5.6) — `ScaledQuantity` :
`name`, `value`, `unit`, `type` (linear/sublinear/fixed/…), `fixed: bool` (→ verrou `=`),
`notes: list[str]` (→ notes `--`, vide en C1), `reserve` (optionnel, rempli en C4),
`debug: {rule, coeff, formula, reasoning}` (pour le panneau debug FR7).
[Source : docs/architecture.md#4.3, #5.6]

### Stratégie de matching (archi §5.3 — décision déjà actée)

La table liste des **mots-clés**, pas des regex. Implémentation retenue :
1. **Normaliser** : minuscule + suppression des accents (`é`→`e`, etc.).
2. **Matcher par token entier**, **pas** par sous-chaîne (évite « ail » ⊂ « vol-au-vent »).
3. Parcourir `categories[]` dans l'ordre, retourner la **première** correspondance.
4. Aucun match → défaut `linear`.

Cette stratégie est explicitement demandée par l'AC2 et l'architecture. À durcir si des faux positifs sont constatés (hors scope C1).
[Source : docs/architecture.md#5.3]

### Conventions de code (alignées sur l'existant `app/epicure/loader.py`)

- `from __future__ import annotations` en tête ; type hints PEP 585 (`list[tuple[...]]`, `dict[str, int]`).
- Python 3.10+ (le repo utilise déjà cette syntaxe).
- Docstring de module en français, code/identifiants/clés JSON en anglais (convention projet, archi en-tête).
- Chemins via `pathlib.Path(__file__).resolve().parents[...]` (cf. `loader.py` ligne 21). Depuis `app/scaling/`, la racine repo est à `parents[2]`, donc la table est à `parents[2] / "docs" / "scaling" / "table-scaling-sale.json"`.
- Lecture JSON : `json.loads(path.read_text(encoding="utf-8"))` (même patron que `loader.py`).
- **Pas de nouvelle dépendance** : `json`, `unicodedata`, `pathlib`, `dataclasses` (ou `functools`) suffisent. Pydantic est disponible (FastAPI) mais une **dataclass** suffit et reste plus légère pour un module pur — au choix, rester cohérent.
