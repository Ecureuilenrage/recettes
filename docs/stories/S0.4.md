## Story

En tant que **développeur du projet (chaîne de génération `.cook`)**,
je veux **un `.cook` minimal mais complet qui exerce tous les marqueurs Cooklang du projet, une auto-vérification structurelle déterministe qui prouve qu'il est bien formé, et une procédure reproductible d'ouverture dans Obsidian (plugin `cooklang-obsidian`) avec capture finale**,
afin de **valider de bout en bout que le format `.cook` produit par le templating maison (décision S0.3) est compatible Obsidian, et de débloquer l'émission `.cook` de la couche 4 (D3)**.

## Acceptance Criteria

1. **AC1 — `.cook` minimal mais complet** : un fichier `.cook` existe et exerce **tous** les marqueurs Cooklang du projet (architecture §8.4) : frontmatter `servings`, `@ingrédient{quantité%unité}`, `#ustensile`, `~{durée}`, verrou `=` (valeur figée type température), note `--`. UTF-8, accents corrects.
2. **AC2 — Bien formé (vérifié)** : une **auto-vérification structurelle déterministe** (regex sur les marqueurs `@ # ~ {…%…} = --` + frontmatter) est **documentée et exécutée**, et son résultat réel est **consigné**.
3. **AC3 — Procédure Obsidian reproductible** : la procédure d'installation du plugin `cooklang-obsidian`, de placement du fichier et le **rendu attendu** (liste d'ingrédients, ustensiles, minuteurs) sont documentés sous forme de **checklist de conformité**. La **capture d'écran** est l'étape manuelle finale, documentée comme « à exécuter par l'utilisateur », avec un emplacement réservé.
4. **AC4 — Conclusion** : le rapport conclut que le format `.cook` du templating maison est compatible Obsidian (ou consigne les réserves), en distinguant ce qui est vérifié programmatiquement de l'étape manuelle.

### Contexte architectural (à respecter impérativement)

- **Décision S0.3 (templating maison + validation)** : le projet **génère** le `.cook` par templating Python et le **valide** (regex maison en v1, paquet `cooklang-py` pur-Python sous réserve de confirmation — RZ5). S0.4 est le **vrai test de conformité de bout en bout** annoncé par cette décision.
  [Source : docs/decisions-techniques.md#3 — Implications « S0.4 (ouverture dans Obsidian) reste à faire — c'est le vrai test de conformité de bout en bout »]
- **Format `.cook` du projet (architecture §8.4)** : trois marqueurs `@ingrédient{quantité%unité}`, `#ustensile`, `~{durée}` ; frontmatter `servings` ; verrou `=` (figé, posé par le moteur de scaling pour le type `fixed`) ; notes `--` (portées par le moteur scaling et par le LLM avec étiquettes `[SÉCURITÉ]/[TECHNIQUE]/[PRÉFÉRENCE]`).
  [Source : docs/architecture.md#8.4-Format-Cooklang]
- **Verrou `=` = type `fixed`** : la température n'est jamais multipliée au scaling ; elle porte le verrou `=` Cooklang (déjà implémenté côté moteur, C1 `scale("four",180,…) → fixed=True`). Le smoke-test ancre ce marqueur dès la validation de format.
  [Source : docs/architecture.md#5.2 ; docs/scaling/table-scaling-sale.json#categories temperature ; docs/stories/C1.md AC5]
- **Plugin Obsidian** : `cooklang/cooklang-obsidian` (Community Plugin « Cooklang »).
  [Source : docs/recherche-ouverte.md §E (Cooklang) ; docs/decisions-techniques.md#3]
