## Story

En tant que **développeur de la base technique (couche 2)**,
je veux **des loaders purs et déterministes (`load_safety`, `load_cuisines`) qui chargent la sécurité alimentaire et découvrent dynamiquement les cuisines `cuisine-*.json`, plus une API `techniques_for(cuisine, ingredient, constraints)` qui renvoie les techniques applicables en excluant celles dont un ustensile requis est interdit, et un `safety_for(food_type)` qui retourne la ligne de sécurité d'une protéine**,
afin de **fournir au générateur LLM (couche 4) une base de vérité dans laquelle il choisit — techniques, températures, sécurité — sans jamais rien inventer, tout en restant modulaire par cuisine (ajouter une cuisine = déposer un fichier, sans toucher au code)**.

## Acceptance Criteria

1. **AC1 — Chargement sécurité (lecture seule, unique)** : `load_safety()` charge `docs/base-technique/safety-temperatures.json` **une seule fois** (cache module-level) en **lecture seule**, et retourne une `SafetyTable` typée (liste de `SafetyStandard`). `safety_for(food_type)` retourne la ligne applicable (`SafetyStandard`) ou `None`, avec un **matching insensible à la casse et aux accents**. Le wording exact des valeurs (notes, libellés `foodType`) **n'est pas** assumé (un autre agent édite ce fichier en parallèle) : seul le **schéma de clés** est stable (`foodType, minInternalC, minInternalF, restMinutes, critical, source, note`).
2. **AC2 — Découverte modulaire des cuisines (OA3)** : `load_cuisines()` **découvre dynamiquement** tous les `docs/base-technique/cuisine-*.json`, indexés par `meta.id` (ex. `italian_savory_v1`). **Aucune cuisine codée en dur**. Chargé **une seule fois** (cache module-level), en lecture seule. Ajouter une cuisine bien formée = déposer un fichier, **sans modifier le code**.
3. **AC3 — `techniques_for` exclut les techniques à ustensile interdit** : `techniques_for(cuisine, ingredient, constraints)` retourne la liste des `Technique` de la **cuisine demandée** (clé `meta.id`), et **exclut** toute technique dont un `requiredTools` tombe dans l'ensemble des ustensiles interdits déduits des contraintes utilisateur (`cookwareConstraints`). Exemple normatif : avec `Constraints(no_cookware=["pas_de_four"])`, `searing_braising` (qui requiert « four ») est **exclue**, et `pasta_al_dente` / `risotto` / `soffritto` / `sugo_pomodoro` sont **conservées**.
4. **AC4 — Types de sortie (dataclasses stdlib) + module pur** : la sortie utilise des **dataclasses stdlib** `SafetyStandard`, `SafetyTable`, `Technique`, `Cuisine`, `Constraints` (champs `diet: list[str]`, `no_cookware: list[str]`, `highlight: str | None`, alignés sur archi §9.1). Module **pur / déterministe** : même appel → même résultat ; aucune nouvelle dépendance (pas de Pydantic ici).

## Dev Notes

### Contexte architectural (à respecter impérativement)

- **Couche 2 = base technique grounded (archi §3.1, §4.2)** : `app/knowledge/` fournit techniques, températures, ustensiles requis, sécurité et le mapping contraintes → cookware interdit. Elle **n'invente rien** et **ne génère pas de texte** ; elle est **déterministe (lecture JSON)**. Le LLM **choisit** dedans (FR3).
  [Source : docs/architecture.md#3.1-Responsabilités-de-chaque-couche ; docs/architecture.md#4.2-Couche-2]
- **Signatures prescrites (archi §4.2 — ne pas dévier)** :
  ```python
  def load_safety() -> SafetyTable: ...          # docs/base-technique/safety-temperatures.json
  def load_cuisines() -> dict[str, Cuisine]: ...  # découvre tous docs/base-technique/cuisine-*.json
  def techniques_for(cuisine: str, ingredient: str | None, constraints: Constraints) -> list[Technique]: ...
  def safety_for(food_type: str) -> SafetyStandard | None: ...
  # + helper interne ustensiles interdits (B3) ; forbidden_cookware public = B4
  ```
  [Source : docs/architecture.md#4.2-Couche-2]
- **Découverte modulaire (OA3, D11, schema §4)** : `load_cuisines()` scanne `docs/base-technique/` pour `cuisine-*.json`, clé = `meta.id`. **Aucune cuisine en dur**. Ajouter une cuisine = déposer un fichier conforme à `schema.md`, sans toucher au code (validé en F1).
  [Source : docs/architecture.md#1.3-OA3 ; docs/architecture.md#12 (D11) ; docs/base-technique/schema.md#4-Modularité]
- **Trois niveaux d'autorité** : `SÉCURITÉ` > `TECHNIQUE` > `PRÉFÉRENCE`. `safety-temperatures.json` est **autoritatif et transverse** ; `critical: true` ⇒ aucune flexibilité. B3 **expose** ces données mais n'implémente pas encore la validation (D2).
  [Source : docs/architecture.md#4.2 ; docs/base-technique/schema.md#1]

### Périmètre B3 vs B4 (découpage explicite — éviter tout doublon)

- **B3 (cette story)** implémente : les loaders (`load_safety`, `load_cuisines`), `techniques_for`, `safety_for`, et un **calcul interne** des ustensiles interdits **suffisant** pour faire passer l'exclusion (AC3). Le helper est **interne** : `_forbidden_cookware(cuisine, constraints) -> set[str]`, matching simple (clé de `no_cookware` → liste de `cookwareConstraints`, normalisée casse/accents).
- **B4 (story suivante, même zone `app/knowledge/`)** formalisera l'**API publique** `forbidden_cookware(cuisine: str, constraints: Constraints) -> set[str]` avec un matching **plus robuste** (« four » ↔ « cocotte au four », tolérance accents/casse poussée, sous-chaînes/synonymes) et la **politique « remplacer ou refuser proprement »** (cf. `llmConstraints` du JSON). B4 **promouvra/affinera** le `_forbidden_cookware` de B3 (le rendre public, durcir le matching) sans casser `techniques_for`.
- **Conséquence pour le dev B3** : écrire `_forbidden_cookware` de façon assez générale pour que B4 le promeuve, mais **ne pas** anticiper le matching avancé de B4. Garder l'exclusion d'AC3 simple et déterministe.
  [Source : docs/architecture.md#4.2 (B4 = `forbidden_cookware` ; remplacer/refuser) ; docs/backlog.md (B3/B4) ; docs/sprint-plan.md (B3 → B4)]

### Décisions par défaut (mode non-interactif — documentées)

- **Filtrage par `ingredient` = souple (v1 italien)** : `techniques_for` **n'écarte pas** une technique par défaut si l'ingrédient ne matche pas explicitement. Le rejet **dur** est réservé aux **contraintes matérielles** (cookware interdit). Cohérent avec la décision D14 (filtrage cuisine souple côté couche 1) et archi §4.1.
  [Source : docs/architecture.md#4.1 (D14, filtrage souple) ; docs/architecture.md#12 (D14)]
- **Cuisine inconnue → liste vide** : `techniques_for` sur une clé `meta.id` absente renvoie `[]` (pas d'exception). Choix retenu pour la robustesse de l'orchestrateur (couche 4 / API) ; l'API web (§9.1) traduit déjà « cuisine inconnue » en `422` en amont. Documenté ici comme décision par défaut.
  [Source : docs/architecture.md#9.1 (codes 422 cuisine inconnue) ; décision par défaut B3]
- **Dataclasses stdlib, pas Pydantic** : conformément aux conventions projet (modules purs, `dataclasses` stdlib), `app/knowledge/` utilise des `@dataclass`. L'archi §4.2 mentionne « Pydantic recommandé » mais laisse le choix « ou dataclasses » ; on retient dataclasses pour rester pur/léger et cohérent avec `app/scaling/` (C1-C5). La conversion vers Pydantic, si requise par l'API (E1), se fera à la frontière FastAPI, pas dans la couche 2.
  [Source : docs/architecture.md#4.2 (« Pydantic recommandé … ou dataclasses ») ; consignes projet (dataclasses stdlib)]
